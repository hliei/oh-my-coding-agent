## Answer

All Reference observations and citations below use committed revision `0e6909f050eeb15e8f6c05185511f3788357ddb3`.

### Observation envelopes and shared loop

The four low-level entries and `Agent` share one loop implementation. Their envelopes cover A/L/T/E/C across admission, ordered events, Model and Tool effects, terminal values, state reduction, cancellation, failure ownership, and later reuse. Tool execution and listener/`AgentEventSink` delivery have their own A/L/T/E/C sub-envelopes inside that loop.

A **Run** is one admitted invocation. A **Turn** is one Assistant response plus its complete Tool batch and source-ordered Tool Results. New-prompt entries emit their prompt Messages inside the first Turn; continuation adds no seed. Another Turn begins only when the completed Tool batch requires another Model response. Ordinary success, Model error, and clean abort emit one `agent_start` and one `agent_end`; a lifecycle carrier failure truncates the trace and emits no synthetic end.

`agentLoop*()` versus `runAgentLoop*()` differ only in EventStream versus awaited-sink carrier, while prompt versus continue differs only in seed. Steering and follow-up queues do not exist in v0.

### Context ownership and results

Every activated low-level operation creates a private working Context with copied Message and Tool tuples. It never mutates the supplied `AgentContext`. New-prompt results contain the prompt seeds plus every Assistant, Tool Result, and synthetic terminal Message produced by that Run; continuation results contain only produced Messages. The full working history is not returned.

`AgentEvent.AgentEnd.messages`, EventStream `result()`, and awaited `runAgentLoop*()` return the identical immutable tuple. Lifecycle failure has no partial tuple return. Stateful `Agent` derives history only through event reduction and finishes with a value-equal suffix.

### Admission and Agent-owned state

`Agent.prompt(text)` constructs `UserMessage(content=text, timestamp=<admission Unix milliseconds>)`; empty text is valid. A single nominal `AgentMessage` or nonempty Message sequence is validated, copied, and preserved. The effective Context tail after a new prompt must be User or Tool Result. `continue_()` adds no Message and requires an existing User or Tool Result tail. Carrier misuse is `TypeError`; empty seed or invalid tail is `ValueError`. A busy Agent raises `LifecycleError(code="busy")`. Every rejection precedes Run ownership, event, state change, and effect.

Synchronous `agentLoop*()` factories perform static validation before returning a dormant stream; lazy operations validate on first await. Admission atomically installs the Run and its signal, sets `isStreaming=True`, clears `streamingMessage`, `pendingToolCalls`, and `errorMessage`, then emits `agent_start`.

`Agent.state` retains one live identity. `systemPrompt`, `model`, `tools`, and `messages` are assignable only while idle; Tool and Message assignments validate and snapshot tuples before atomic replacement. Lifecycle fields are read-only. Busy assignment or `reset()` raises busy without mutation. Idle `reset()` clears only Messages and error text, preserving system prompt, Model, and Tools. `initialState` is copied seed data, never shared mutable identity.

### Closed Agent events and state reduction

`AgentEvent` is an externally sealed base with these final nested Public Value Records, fixed Reference `type` strings, and exact camelCase fields:

- `AgentStart`; `AgentEnd(messages)`
- `TurnStart`; `TurnEnd(message, toolResults)`
- `MessageStart(message)`; `MessageUpdate(message, assistantMessageEvent)`; `MessageEnd(message)`
- `ToolExecutionStart(toolCallId, toolName, args)`; `ToolExecutionUpdate(toolCallId, toolName, args, partialResult)`; `ToolExecutionEnd(toolCallId, toolName, result, isError)`

The ordinary grammar is `agent_start`, then one or more `turn_start` / optional seed Message pairs / Assistant start-update*-end / Tool lifecycles / source-ordered Tool Result Message pairs / `turn_end`, then `agent_end`. An Assistant terminal value always receives start/end even if no partial update arrived. Events are immutable validated snapshots; there is no mapping or unknown-event escape.

Before each listener, Message start/update replaces only `streamingMessage`; Message end clears it and appends once to a new history tuple. Tool start adds and Tool end removes the id through fresh pending frozensets; Tool update changes no state. Turn end sets `errorMessage` only for an error/aborted Assistant. Synthetic abort commits matching error text after its Message-end barrier and before `agent_end`.

During `agent_end` listeners, `isStreaming` remains true and the active signal remains installed. After terminal listeners settle, the owner atomically clears the signal, sets streaming false, confirms no pending Tool, and wakes operation/idle waiters.

### Model Turn and ordinary error

Model start/update/end events project to the corresponding Agent Message events. Model error or abort carries no Tool execution. A `stop` or `toolUse` Assistant with Tool Calls enters Tool processing; either reason without calls ends normally. A `length` Assistant without calls ends, while `length` with calls executes none and creates recoverable truncated-call Tool Results so a later Model Turn can reissue them.

A thrown or invalid `streamFn`, invalid stream protocol/terminal payload, and selected auth/Provider/transport/wire/Usage failure settle as one `AssistantMessage(stopReason="error")`. With no partial it uses empty content, zero Usage, and active Model identity; otherwise it preserves the latest legal cumulative snapshot. The loop emits one end, `turn_end(..., toolResults=())`, and `agent_end`; returns normally; sets matching Agent error text; performs no retry; and permits a caller-started fresh Run. Arbitrary custom-stream exceptions normalize privately to `ModelsError(code="stream")` with fixed redacted public text and a private cause.

### Tool admission, execution, and projection

Before any Tool attempt, one effect-free batch scan requires every `toolCallId` to be nonempty and unique within that Assistant. Empty ids and every occurrence of a duplicate id are rejected independently; unique calls remain eligible. Ids may recur in later Assistant Messages.

For each Call in source order, `ToolExecutionStart` begins the attempt and carries original immutable arguments; it does not mean the callable has started. Runtime then requires exactly one Tool-name match, runs effect-free `prepareArguments`, and converts/validates a fresh argument tree. Rejection creates a recoverable error end/result and never calls `execute`. The public before/after Tool hook group is absent.

Only after complete batch preflight may effects start. Global or any called Tool's sequential declaration serializes the whole batch; otherwise approved callables start concurrently. Same-Tool start/update/end causality is fixed; cross-Tool updates and ends may interleave. Every started Tool and accepted update settles before Tool Result Messages project in original Call order and before any next Model effect.

`onUpdate()` synchronously validates/snapshots a result into that Tool's FIFO and returns `None`; Runtime asynchronously drains it through awaited event barriers. Invalid update is unpublished and irreversibly fails the Tool even if caught. Calls after execute settlement or cancellation cutoff are ignored. Partial `terminate` is observational only.

Normal final result closes update admission, drains updates, and emits one successful end. Exception, non-awaitable, or invalid final value retains/drains earlier valid updates and emits a recoverable error end/result, never a Run lifecycle failure. Every Runtime Tool error has one Text block, empty-object details, no termination, and `isError=True` in both end and Message. A normally returned valid result is always a Tool Outcome with `isError=False`, even when its detailed content reports an expected negative domain outcome; only a true Tool Failure takes the error path.

Canonical JSON string quoting is `q(x)`. Runtime templates are:

- `Tool call id must not be empty`
- `Tool call id {q(id)} is duplicated in one assistant message`
- `Tool {q(name)} was not found`
- `Tool {q(name)} matched more than once`
- `Tool {q(name)} argument preparation failed`
- the accepted ticket-05 schema-validation text, unchanged
- `Tool call {q(name)} was not executed: the response hit the output token limit, so its arguments may be truncated. Re-issue the tool call with complete arguments.`
- `Tool {q(name)} execution failed`
- `Tool {q(name)} execute must return an awaitable`
- `Tool {q(name)} produced an invalid update`
- `Tool {q(name)} produced an invalid result`
- `Tool {q(name)} execution was cancelled`

Raw exception text/repr, arguments, schema, stack, paths, and arbitrary details never enter public events or history.

### Continuation and termination

After full batch settlement, another Turn starts unless a nonempty batch has every finalized outcome successful with final `terminate=True`. Any false/None, rejection, or execution failure continues. Even a unanimously terminating batch projects every result and `turn_end` before `agent_end`. There is no hidden Turn, token, or cost limit and no `shouldStopAfterTurn`; a continuing Run ends only through natural stop, unanimous termination, Model error, owner cancellation, or lifecycle failure.

### Cancellation and lifecycle failure

Clean cancellation retains already published Messages, updates, and finalized outcomes. Model cancellation finalizes its cumulative Assistant as aborted. During Tool work, completed outcomes remain real; started/unsettled, approved/not-started, and not-yet-preflighted Calls receive cancelled error Results so every Assistant Tool Call has one source-ordered Tool Result Message. A Call that emitted start receives one end; a Call untouched when preflight stopped receives no fabricated start/end, only its cancelled Message.

After Tool projection the original Turn ends. If Model did not already produce an aborted tail, Runtime appends outside a new Turn one empty, zero-Usage Assistant with active Model identity, `stopReason="aborted"`, `errorMessage="Operation aborted"`, and terminal timestamp, then emits `agent_end` without a Model effect. `Agent.abort()` cleanly settles Agent methods normally; owner-task cancellation commits the same state before re-raising `CancelledError`.

Cleanup attempts all independent actions and retains ordered causes. If all work is confirmed stopped despite errors, no aborted tail or `agent_end` is fabricated; observers receive `LifecycleError(code="cleanup")`, Agent normalizes idle runtime fields, and published history remains. If any work/resource remains unconfirmed, there is no terminal classification: Agent stays active/non-idle with aborted signal and unresolved pending ids and rejects new work/mutation until real settlement.

For listeners, state reduction happens first and every member of the fixed current snapshot runs in registration order even after the first exception. Later events/effects stop; ordered callback errors precede cleanup errors in `LifecycleError(code="listener")`; history is not rolled back or patched. A failed `AgentEventSink` receives nothing later and `runAgentLoop*()` raises `LifecycleError(code="event_sink")` with no partial result. Ordinary-event callback failure has no `agent_end`; terminal-listener failure changes only the public await carrier, not the already committed terminal classification/history. Actual pending owner-task cancellation retains cancellation provenance.
